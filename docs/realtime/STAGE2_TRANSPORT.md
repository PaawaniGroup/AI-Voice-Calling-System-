## Gate G1 (round trip over the persistent connection, median <= 40 ms)
Caveat I have not been able to resolve offline: the 40 ms is only reachable from a host near the GPUs. From the operator's PC the path to RunPod passes the home link first (PC to the Cloudflare edge measured about 57 ms average ICMP earlier, MEASURED), so a Pod round trip from the PC is likely above 40 ms (ESTIMATE). So the probe takes `--declared-from pc|cloud`; G1 is judged only for `cloud`; a `pc` run is informational. The operator must say where the service will really run.

### G1 REQUEST design
Action: one Pod (cheapest 24 GB-class, max price per hour enforced), start the probe server (`deploy/rt_workers/common.py` with a no-model engine), run `rt_rtt_probe.py` (200 pings + 200 warmups), delete the Pod. Hard deadline 5 minutes; cost $0.057 at $0.00019/s, $0.090 at $0.0003/s; cap $0.10. Stop at the cap, first 401/403, or 3 consecutive errors. Deletion is verified by listing Pods read-only at start and end; if a Pod might still run: "ACTION NEEDED: DELETE POD NOW". Undo: delete the Pod, revoke the key. Launch conventions follow `tools/phase3/launch_pod.py` (key as a file path only, balance margin check).

## A Pod reset changes its address
Per the Pod docs (2026-10-27): the external TCP port changes whenever the Pod resets; the public IP is stable on Secure Cloud and may change on Community Cloud. The client therefore accepts an optional per-service `resolver` (async, returns the current ws(s):// URL): it is asked before every RE-connect and between failed connect attempts; a failing, empty or non-websocket answer keeps the old address and never raises; the new address is kept for later reconnects (`counters["rediscovered"]`). The resolver itself (a read-only Pod lookup through the RunPod API, or a fixed Secure Cloud address) is Stage 3 work and is not wired to any endpoint; with none configured the old address is retried and the request falls back to the queue path. Tested with a mock address book (`test_rt_connection.py`, four tests).
## How the transport is secured on a public TCP port
**Caller audio is never sent unencrypted by this design.** The first draft left TLS to "the host"; that was wrong for a Pod's raw TCP port (no proxy, no TLS of its own), and it is fixed (all flag-guarded: nothing runs unless a tenant switches `rt_transport` to persistent):
- **Encryption.** The client accepts `wss://` only. Plain `ws://` is accepted only for a loopback address (the local end of a private tunnel: an SSH `-L` forward, WireGuard/Tailscale with a local forward), or when code passes `unsafe_allow_plain_ws=True` to the constructor. That argument is not in `RtConfig`, not a tenant-config key, not an environment default; a tenant cannot switch encryption off. `put_config` refuses a public `ws://` endpoint, the client refuses it again at construction (no byte sent), and a resolver cannot move a client to one (tests).
- **Certificate.** `wss://` verifies the certificate chain and host name (a Pod behind a domain with a CA certificate), or, for a self-signed certificate on a raw TCP port, **pins** it: tenant key `rt_pins` {stt|tts: SHA-256 of the DER certificate, 64 hex characters; a fingerprint is public, not a secret}; a different certificate closes the socket and is an `auth` error (`pin_mismatch`). The probe takes `--pin-sha256`. The self-signed certificate is made on the Pod at start (openssl, one command in the Stage 3 launcher notes) and its fingerprint is printed to the operator: not a secret.
- **Server side.** `common.serve_forever` binds `RT_BIND` (default 127.0.0.1), terminates TLS itself with `RT_TLS_CERT` / `RT_TLS_KEY`, and refuses to start on a non-loopback address without a certificate (`--unsafe-plain` on the command line, never an environment default, for a closed test network only).
- **Authentication.** A shared secret (an environment variable of each side, referenced by NAME in tenant config, never stored or logged) signs a token `call.exp.nonce.sig` (HMAC-SHA256) bound to the call id, valid 120 s, and **single-use**: the server remembers the nonce until expiry (bounded cache; a full cache refuses rather than forgets). A token captured on the wire (impossible under TLS, but the layer does not rely on that) cannot be replayed on a new connection, nor used for another call id.
- **Network allowlist.** Not implemented in the application: a Pod's TCP port has no firewall of its own on RunPod (UNVERIFIED), so the secret + TLS carry the load. If the app host has a fixed address, an IP allowlist on the Pod's side is a cheap extra layer (operator choice, UNVERIFIED how RunPod lets one set it).

### What a stranger who finds the port can do
**Nothing useful.** Measured by the tests (SIMULATED, in-memory sockets, the real server code): a client that sends a request without a hello, garbage, binary, an oversize first message, or nothing at all, gets at most one `error` and the socket is closed (silence: after the 5 s hello timeout); a hello with a wrong, expired, other-call, wrong-secret, malformed or replayed token is answered with one error code and closed; in none of these cases does an engine run, and no audio or text is ever returned. What remains is the cost of a handshake attempt: a stranger can open sockets and make the server spend up to 5 s per connection on them (a resource nuisance, not access); the TLS handshake reveals nothing but the certificate. Not covered: a stranger who also holds the shared secret (then they are the operator: rotate the secret), and a Pod host operator reading GPU memory (outside this design).
Residual risks to state plainly: the secret must reach each side without being printed; one process-wide replay cache means a server restart forgets nonces (tokens live 120 s; accept); the per-IP connection rate limit is not built (UNVERIFIED need).
